# Demo assets

Synthetic identity documents for the live re:Invent demo — four personas, one per jurisdiction
the applicant app offers (US/UK/AU/JP), each a single-page PDF laid out like a real ICAO 9303
TD3 data page: header band, portrait, paired English/French field labels, and a genuine two-line
machine-readable zone with correctly computed check digits.

Generated by `gen_documents.py` with **no image-library dependency** — the PDF is hand-assembled
and photos are embedded by passing JPEG bytes straight through PDF's `DCTDecode` filter.

| File | Use when you pick |
|---|---|
| `generated/demo-us-01-passport.pdf` | United States |
| `generated/demo-uk-01-drivers_license.pdf` | United Kingdom |
| `generated/demo-au-01-national_id.pdf` | Australia |
| `generated/demo-jp-01-passport.pdf` | Japan |

## Regenerate

```
make demo-assets
# or:
./.venv/bin/python demo-assets/gen_documents.py
```

## Adding a photo

Drop any **JPEG** into `demo-assets/photos/` and re-run. Lookup order per persona:

1. `demo-us-01.jpg` (persona-specific)
2. `default.jpg` (all four)
3. any other `.jpg`/`.jpeg` in the folder — so a photo straight off a camera works without
   renaming it

Must be JPEG, not PNG: the generator embeds the compressed bytes directly via `DCTDecode`, which
has no PNG equivalent. Greyscale or RGB only — CMYK is refused rather than rendered inverted.
With no photo, the portrait frame is drawn empty and labelled, which is not an error.

## These are specimens, deliberately

The layout is structurally faithful — including real MRZ check digits, verified in
`tests/test_gen_documents.py` against ICAO 9303's own published test vectors — because an
audience reads "real system" from the MRZ more than from any other detail, and a wrong check
digit is exactly what someone in the room notices.

They stay unmistakably synthetic on purpose:

- A banner naming the document kind ("SPECIMEN - NOT A REAL TRAVEL DOCUMENT" / "... DRIVING
  LICENCE" / "... IDENTITY DOCUMENT"), plus a footer stating no legal validity.
- Every name, date, number, and address is fabricated (D-03's synthetic-data convention, same
  rationale as `tools/kyctools/data/sanctions.py`).
- No persona name collides with any entry in `sanctions.py`'s `ALL_ENTRIES`/`PEP_ENTRIES` —
  enforced by test, so a demo run cannot produce an unintended sanctions/PEP hit in the review
  queue.

Making these indistinguishable from genuine documents would be forgery, not a better demo.
Structurally faithful *and* clearly marked gets the demo value with none of that.

## Using them in the demo

1. Applicant app (`npm run dev:applicant`, port 5173) — sign in.
2. Liveness step: use your own face. `FaceLivenessDetector` needs a real live capture; no file
   is involved.
3. Documents step: upload the PDF matching the jurisdiction you chose at intake.

Note: `api/applicants.py` never reads the document bytes — only `type`/`key`/`bucket`/
`issuingCountry` metadata reaches the case record, so document content has no effect on the
Phase 1 outcome. The realism is for the audience, not the pipeline.
