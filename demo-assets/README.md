# Demo assets

Synthetic identity documents for the live re:Invent demo: seven personas, each a single-page
document laid out like a real ICAO 9303 TD3 data page (header band, portrait, paired
English/French field labels, and a genuine two-line machine-readable zone with correctly
computed check digits). Each is written as a PDF and as a JPEG: **print the page** (the PDF, at
100% scale) to hold up to the webcam, and keep the **JPEG** to upload when the camera will not do.

Generated by `gen_documents.py` with **no image-library dependency** — the PDF is hand-assembled
and photos are embedded by passing JPEG bytes straight through PDF's `DCTDecode` filter.

## The personas

The US is the only jurisdiction this build decides automatically (`DECIDED_JURISDICTIONS`), so
every screening scenario is a US persona. Each persona's screening outcome is pinned by
`tests/test_gen_documents.py`, which runs the real matcher over the identity the screening tool
builds from the case record.

## Regenerate

```
make demo-assets
# or:
./.venv/bin/python demo-assets/gen_documents.py
```

## Photos: the face must be the presenter's

The tools compare the portrait on the document with the frame captured by the liveness check.
So the photo printed on a persona's document has to be the face of whoever does that persona's
liveness check on stage; any other face is a face-match failure, and the case goes to a person.

Drop **JPEGs** into `demo-assets/photos/` and re-run. Lookup order per persona:

1. `demo-us-02.jpg` (persona-specific: one per presenter)
2. `default.jpg` (every persona)
3. any other `.jpg`/`.jpeg` in the folder

Must be JPEG, not PNG: the generator embeds the compressed bytes directly via `DCTDecode`, which
has no PNG equivalent. Greyscale or RGB only — CMYK is refused rather than rendered inverted.
With no photo, the portrait frame is drawn empty and labelled, which is not an error — but the
face match will then fail. Real photos are gitignored; keep them local.

## These are specimens, deliberately

The layout is structurally faithful — including real MRZ check digits, verified in
`tests/test_gen_documents.py` against ICAO 9303's own published test vectors — because the tools
genuinely read the machine-readable zone and verify its check digits, and an audience reads
"real system" from the MRZ more than from any other detail.

They stay unmistakably synthetic on purpose:

- A banner naming the document kind ("SPECIMEN - NOT A REAL TRAVEL DOCUMENT" / "... DRIVING
  LICENCE" / "... IDENTITY DOCUMENT"), plus a footer stating no legal validity.
- Every name, date, number, and address is fabricated (D-03's synthetic-data convention, same
  rationale as `tools/kyctools/data/sanctions.py`), and the screening list they meet is
  synthetic too.

Making these indistinguishable from genuine documents would be forgery, not a better demo.
Structurally faithful *and* clearly marked gets the demo value with none of that.

## Using them in the demo

1. The console (`cd frontend && npm run dev`, http://localhost:5173) — sign in, Live demo.
2. *New application* → the persona. The app opens with its details filled in.
3. ID document: *Take a photo*, and hold the printed page up to the webcam, inside the frame.
   Only the inside of the frame is kept, so the presenter's own face stays out of the document
   photo, which the face match compares with the selfie. *Upload a photo instead* takes the
   persona's JPEG.
4. Selfie video: the presenter's own face, live. `FaceLivenessDetector` needs a real capture;
   no file is involved.
5. Review, then Submit.

The document is evidence, not decoration: the document tool reads it (Textract, then the MRZ
parsed and check-digit verified), the face-match tool compares its portrait with the liveness
frame, and the rules decide on what those tools recorded. The run-of-show is in
`docs/RUNBOOK.md`.
